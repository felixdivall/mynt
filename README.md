# Sail

Sail is a source language for NetSuite that understands records, fields,
script entry points, and platform built-ins before it emits SuiteScript 2.1.
This repository is the v0 spike: one file is one script, field access is
checked against a schema, record types are compile-time symbols, and `N/*`
dependencies are inferred.

## Commands

```bash
pnpm install
pnpm test                                    # vitest: parser, binder, end-to-end
pnpm sail check examples/customer.sail       # diagnostics only
pnpm sail build examples/scheduled.sail      # writes examples/scheduled.js
pnpm build && node bin/sail.js check examples/customer.sail

pnpm sail account add sandbox                # one-time: account id + OAuth client id (stored per user)
pnpm sail auth login sandbox                 # browser login; tokens go to the OS keychain
pnpm sail account use sandbox                # writes sail.json { "account": "sandbox" }
pnpm sail schema pull                        # writes .sail/schema/sandbox.json (commit it)
pnpm sail check src/customer.sail            # now compiles against the pulled schema
```

## Script kinds

A `.sail` file is exactly one NetSuite script. The entry points in it decide
the script type; there is no wrapper declaration. Mixing kinds in one file is
an error (SAIL1015).

### User Event

```sail
beforeSubmit create | edit (customer: Customer) {
    log.audit("Customer saved")
    customer.comments = "Managed by Sail"
}
```

The parameter type is both the type of the bound record and the deployment
target. Every entry point in the file must name the same record type.
Hooks: `beforeSubmit`, `afterSubmit`. The event filter is optional and takes
any of the `context.UserEventType` names: `create`, `edit`, `view`, `copy`,
`delete`, `xedit`, `approve`, `cancel`, `reject`, `pack`, `ship`, `dropship`,
`specialorder`, `orderitems`, `paybills`.

### Scheduled

```sail
scheduled {
    let customer = load Customer("123")

    log.debug(customer.email)
}
```

Generated:

```js
/**
 * @NApiVersion 2.1
 * @NScriptType ScheduledScript
 * @NModuleScope SameAccount
 * Generated by Sail from examples/load-customer.sail.
 */
define(["N/log", "N/record"], (log, record) => {
    function execute(context) {
        const customer = record.load({
            type: record.Type.CUSTOMER,
            id: "123"
        });

        log.debug({
            title: "execute",
            details: customer.getValue({
                fieldId: "email"
            })
        });
    }

    return { execute };
});
```

## Records and the persistence lifecycle

Sail distinguishes a record's domain type from who owns its persistence. Both of the following are a `Customer`, with the
same fields and the same checks, but they take part in persistence
differently.

### Context records

```sail
beforeSubmit edit (customer: Customer) {
    customer.comments = "Changed"
}
```

The entry point record is the one NetSuite is in the middle of saving.
Changes made in `beforeSubmit` are persisted by NetSuite when the hook
returns, so there is no `save`, and writing one is an error (SAIL1020). In
`afterSubmit` the record is already saved, so writes to it are an error
(SAIL1007); load a fresh copy instead.

### Owned records: `load` and `create`

```sail
scheduled {
    let customer = load Customer("123")
    customer.comments = "Changed"
    save customer
}
```

A record the script obtains itself, by loading an existing one or creating
a new one, is *owned*: writable fields can be assigned, read-only fields and
type checks apply exactly as for context records, and nothing about it
persists except through `save`.

```sail
scheduled {
    let customer = create Customer
    customer.comments = "Created by Sail"
    save customer
}
```

The record operations are one family, all written with a record type:

| Operation | Result | Exists in NetSuite |
| --- | --- | --- |
| `load Customer("123")` | `Customer` | already |
| `create Customer` | `Customer` | after `save` |
| `copy Customer("123")` | `Customer` | after `save` |
| `transform SalesOrder("123") to Invoice` | `Invoice` | after `save` |

Each lowers to the matching `N/record` call (`record.load`, `record.create`,
`record.copy`, `record.transform`) with the same `record.Type` constant or
custom-record id string. A new record (create, copy, transform) does not
exist in NetSuite until its first `save`, so one that some execution path
never saves compiles with a warning (SAIL2001) even if it was never
modified, and a modified owned record whose change reaches the end of the
entry point without a later `save` warns as before; see
[Record lifecycle analysis](#record-lifecycle-analysis). `save` is
statement-only and discards the internal id NetSuite returns. NetSuite
permits only certain transform pairs (sales order to invoice, estimate to
sales order, and so on); Sail does not check the pair, so an unsupported one
fails at runtime.

```sail
scheduled {
    let customer = load Customer("123")
    delete customer
}
```

`delete customer` removes a persisted, owned record. It lowers to
`record.delete({ type, id })`: the type is static, and the id is
`Record.id` for a loaded record or, for a new record deleted after its
save, the value that `save()` returned, which the generated code keeps in a
companion variable. A deleted value is consumed: on any path where the
record may have been deleted, reading or assigning a field, saving, or
deleting it again is an error, and the message says whether it *has* been or
*may have* been deleted. A new record cannot be deleted before it has been
saved on every path reaching the delete, and the context record can never
be deleted, because it is NetSuite's.

Sail does not yet know which record types NetSuite refuses to create (some
system records cannot be); the schema has no such signal, so every record
type is treated as creatable and NetSuite reports the error at runtime.

Generated:

```js
define(["N/record"], (record) => {
    function execute(context) {
        const customer = record.load({
            type: record.Type.CUSTOMER,
            id: "123"
        });

        customer.setValue({
            fieldId: "comments",
            value: "Changed"
        });

        customer.save();
    }

    return { execute };
});
```

## Conditions

```sail
scheduled {
    let customer = load Customer("123")

    if customer.email == "" {
        customer.comments = "Missing email"
        save customer
    }
}
```

Generated:

```js
define(["N/record"], (record) => {
    function execute(context) {
        const customer = record.load({
            type: record.Type.CUSTOMER,
            id: "123"
        });

        if (
            customer.getValue({
                fieldId: "email"
            }) === ""
        ) {
            customer.setValue({
                fieldId: "comments",
                value: "Missing email"
            });

            customer.save();
        }
    }

    return { execute };
});
```

`if condition { ... }` and `if condition { ... } else { ... }` are the only
control flow. The condition is not parenthesized, the `{` goes on the
condition's line, and `else` goes on the line of the `}` it follows (a
newline after `}` ends the statement). There is no `else if`; nest an `if`
inside the `else` block.

### Bool, comparisons, and logical operators

```sail
if customer.email != "" && (customer.comments == "" || customer.comments == "New") {
    customer.comments = "Ready"
    save customer
}
```

A comparison has type `Bool`, and an `if` condition must be `Bool`. There is
no truthiness: `if customer.email { }` is an error (SAIL1021), because what
`""`, `0`, `null`, and a record reference would mean as conditions is exactly
the ambiguity Sail exists to remove. The literals `true` and `false` are
`Bool`, and a `Bool` can be stored in a local
(`let missing = customer.email == ""`) and used as a condition later.

| Operators            | Defined for      | Result |
| -------------------- | ---------------- | ------ |
| `!`                  | Bool             | Bool   |
| `<` `<=` `>` `>=`    | Number           | Bool   |
| `==` `!=`            | Text, Number     | Bool   |
| `&&` `\|\|`          | Bool             | Bool   |

Precedence, highest to lowest, following JavaScript:

```text
postfix: member access, calls
!
<  <=  >  >=
==  !=
&&
||
```

`&&` and `||` are left-associative. Comparisons do not chain: `a == b == c`
is a syntax error. Parentheses group: `(a || b) && c`. A parenthesized
expression is not a separate syntax node; the inner expression keeps its
structure and its source span widens to include the parentheses.

Both comparison operands must have the same type (SAIL1022:
`customer.email == 10` is an error, not `false`). Records, Bools, and Void
cannot be compared (SAIL1023; use a Bool directly, `if x` or `if !x`), and
Text has no ordering (SAIL1023). `&&`, `||`, and `!` take only Bool
operands (SAIL1024). Numeric literals are written as `10` or `2.5`; there is
no unary minus. A line may break after a binary operator, not before it.

**Short-circuit.** `a && b` evaluates `b` only when `a` is true, and
`a || b` evaluates `b` only when `a` is false. This is part of the language,
not of the backend: when built-ins with effects can appear in expressions,
they inherit it.

**Lowering.** Sail `==` is semantic equality on two values of one type, so it
lowers to JavaScript's strict `===`, and `!=` to `!==`; the loose operators
would only add coercions that Sail never permits in the first place. `&&`,
`||`, and `!` lower to the native operators, which keeps the short-circuit
semantics. The printer knows the JavaScript precedence of every bound
expression form and adds parentheses only where they are needed, so
`(a && b) || c` prints as `a && b || c` while `(a || b) && c` keeps its
parentheses. Long conditions break after `&&`/`||`, one operand per line.

### Block scope

A `let` inside an `if` or `else` block is visible only in that block, and
compiles to a block-scoped `const`. A block cannot redeclare a name that is
visible from an enclosing scope (SAIL1017); sibling blocks may reuse a name.
A record's origin (context or loaded) is a property of its type, so it is
the same inside a branch as outside it: a loaded record can be modified and
saved in either branch and after the `if`.

### Record lifecycle analysis

The binder decides what a value is: its record type, and whether the script
owns it. `src/semantic/analysis.ts` decides what has happened to an owned
record on each path through the entry point. It is a forward analysis over
the bound statements with five sets of state per path: writes not yet
followed by a save, new records (create, copy, transform, per the registry
entry's `result: "new"`) not yet saved, locals saved earlier, locals that
*may* have been deleted, and locals that *have* been deleted on every path.
A write adds itself, a new-record declaration adds its local, `save x`
clears both for `x`, `delete x` marks `x` deleted and drops its pending
writes, and an `if` runs both branches from a copy of the state (a missing
`else` is an empty branch) and joins them: union for everything that means
"may have happened", intersection for "certainly deleted", which only
sharpens the wording from "may have been" to "has been".

Before a statement's effect is applied, its uses of locals are checked
against the may-deleted set: a deleted record cannot be read, assigned,
saved, or deleted again (SAIL1027, SAIL1028), and a new record cannot be
deleted while it may still be unsaved (SAIL1026). At the end of the body,
each unpersisted new record gets one SAIL2001 warning at its declaration,
and each pending write gets one at the write, except that writes to a
record already reported as never persisted are covered by that warning.
Nothing here is a type: the same local is usable before `delete` and
consumed after it.

```sail
customer.comments = "Changed"
if customer.email == "" {
    save customer
}
```

```text
warning SAIL2001: 'customer' may leave this script with unsaved changes: it is modified here, but not every execution path that follows performs 'save customer'
```

## Queries and loops

```sail
scheduled {
    let customers = query Customer
        where email != ""

    for customer in customers {
        let record = load Customer(customer.id)

        if record.comments == "" {
            record.comments = "Reviewed by Sail"
            save record
        }
    }
}
```

`query Customer where ...` is an executed query whose value is a
`Sequence<Customer>`: a materialized, re-iterable collection of rows. Inside
`where`, a bare name is a field of the queried record; a name that is both a
field and a visible local is an error rather than a guess. A condition is
an ordinary Sail expression, type-checked as one, and then translated into a
backend-neutral predicate: a field compared with a literal or a captured
local, a Bool field on its own, and `&&`, `||`, `!` over those. Anything
else, such as comparing two fields, is rejected (SAIL1031).

A row is a `Customer` with a third origin, `query`: a typed, read-only view.
Its fields can be read, and `row.id`, a language property rather than a
schema field, identifies the record for `load`. Assigning, saving, or
deleting through a row is an error (SAIL1030) whose message shows the
load-then-modify form. `for row in rows { ... }` scopes the loop variable
to the body; it is an ordinary local for hover, references, and rename.

Lowering uses `N/query`. A helper emitted once per file builds the query,
requests `id` plus every field the program reads from that query's rows
(planned statically, so `["id", "email"]` rather than the whole record),
sorts by `id` so pages are stable, and collects every page of
`runPaged({ pageSize: 1000 })`, since `run()` stops at 5,000 results and a
Sail loop means every matching row. Comparing a Text field with `""` lowers
to `EMPTY`/`EMPTY_NOT`, because an empty NetSuite field is null; a Bool
field uses `IS`. Only one query executes per `query` expression, however
many loops iterate its result.

The lifecycle analysis treats a loop as running zero or more times: the loop
head's state is the fixpoint of the entry state joined with the body's exit
state, computed by re-running the body with diagnostics suppressed until it
is stable, then once more to report. A record created in the body and never
saved warns; a write and save in the body do not; a conditional `delete`
in the body leaves the record possibly deleted both after the loop and on
the next iteration.

## Sublists

```sail
scheduled {
    let orders = query SalesOrder

    for row in orders {
        let order = load SalesOrder(row.id)

        for line in order.item {
            if line.quantity < 1 {
                line.quantity = 1
            }
        }

        save order
    }
}
```

A sublist is a member of its record: `order.item` has type
`Sublist<SalesOrder.item>`, and `for line in order.item` gives `line` the
type `Line<SalesOrder.item>`. A line is not a record. It has no identity or
persistence of its own: its fields are read and assigned like any field,
with the sublist's own field schema and the same type and read-only checks,
and every write is a write to the parent record, persisted when the parent
is saved. `save line` and `delete line` are errors (SAIL1033) that point at
the parent. Lines of different sublists are different types even when
their fields share names.

What a line may do comes from its parent: a loaded, created, copied, or
transformed record's lines can be written; a context record's lines follow
the same hook rule as its fields (writable in beforeSubmit, not in
afterSubmit); a query row has no sublists at all (SAIL1034), because it is
a projection, not a loaded record. A sublist can only be iterated, on a
named record, so that each line read or write knows the local that owns it.
A created record iterates zero lines; adding or removing lines is not yet
part of the language.

The lifecycle analysis treats a line write as a pending write on the parent
local, so the usual warnings apply: unsaved after the loop, modified after
the parent's last save, or saved on only some paths. A deleted parent makes
its sublist and lines unusable.

```sail
scheduled {
    let order = create SalesOrder

    add order.item {
        item = "100"
        quantity = 2
        rate = 10
    }

    save order
}
```

`add order.item { ... }` appends a line to the sublist of a named record.
The block is an initializer, not a body: each statement is `field = value`,
where the bare name on the left is a field of the sublist and the value is
an ordinary expression in the enclosing scope, so a local named like a field
is just the local. A field may be initialized once (SAIL1035), read-only
fields cannot be initialized, and types are checked as for any assignment.
No line value escapes the block. NetSuite may still reject a line that is
missing a field it requires; Sail does not know which fields those are.
`remove line` removes the line a `for` is on; afterwards the line is
consumed, and reading, assigning, or removing it again is an error
(SAIL1036, SAIL1037) with "has been" or "may already have been" wording by
path, reset on each iteration since each is a different line. Adding to a
sublist while iterating it is refused (SAIL1038). Both operations are
changes to the parent and follow its rules: whether the parent may be
changed here is one function in the binder, shared by field writes, line
writes, `add`, and `remove`.

There is no runtime line object. A loop lowers to an index over
`getLineCount`, reads to `getSublistValue`, and writes to
`setSublistValue` on the parent, all in standard record mode; `load` is
unchanged. `add` lowers to `insertLine` at the current count followed by
`setSublistValue` per field, inside a block so adds can follow each other.
A loop whose body removes its own line lowers to a `while` whose index
advances only when the line was not removed, so iteration stays first to
last and the line that shifts into a removed position is not skipped; a
loop that does not remove keeps the plain `for`. Nothing in this model
needs NetSuite's dynamic mode. In the editor a line is an ordinary local
for hover, references, and rename; `order.` completes body fields and
sublists, marked as such, `line.` completes the sublist's fields only, and
inside an add block the sublist's fields are offered with their
writability.

Sublists are represented in the normalized schema (`sublists` on a record,
each with a label and its own fields) and in the built-in fixture, but
live extraction of NetSuite sublist metadata is not yet validated against
an account; `sail schema pull` does not populate them yet.

## Functions

```sail
fn removeEmptyLines(order: SalesOrder) {
    for line in order.item {
        if line.quantity == 0 {
            remove line
        }
    }
}

fn needsReview(memo: Text) -> Bool {
    return memo == "" || memo == "TBD"
}

scheduled {
    for row in query SalesOrder {
        let order = load SalesOrder(row.id)
        removeEmptyLines(order)
        if needsReview(order.memo) {
            order.memo = "Reviewed by Sail"
        }
        save order
    }
}
```

A file may declare top-level functions beside its entry point. Parameters
are `Text`, `Number`, `Bool`, or a record type; a function returns `Text`,
`Number`, or `Bool`, or nothing. Calls may precede the declaration. There
are no closures, nested functions, overloads, optional parameters, function
values, or recursion. A value-returning function must `return` on every
path; `return` always begins a statement. Functions lower to plain
JavaScript functions in the module.

Records cross a call; lines, sublists, query results, and returned records
do not. A line exists only as an index into its loop, and a returned record
would need its own persistence summary, so both are refused rather than
approximated. A record parameter has origin `parameter`: inside the body
the function may read, write, save, and delete it, and is analyzed as if
the parameter were a persisted, clean record. The lifecycle analysis then
summarizes what the body does to each record parameter (whether it modifies
it, whether a change may still be unsaved when it returns, whether it saves
or deletes on some or every path) and every call applies that summary to
the argument in the caller's own analysis, as if the callee's statements
had run there: an unsaved change inside becomes a pending change on the
caller's record, a save inside clears the caller's pending state, a delete
inside consumes the caller's record. The call also checks the argument's
origin against the summary: a query row never passes (it is not a record
object at runtime), an afterSubmit context record cannot be passed to a
function that modifies it, and a context record in any hook cannot be
passed to one that saves or deletes it. Summaries are computed in call
order, which is why recursion is refused (SAIL1043) rather than
approximated.

## Locals and record types

`let name = expression` declares an immutable local whose type is inferred
from the initializer. A local may not be redeclared in the same scope, and an
entry point parameter counts as declared. There is no reassignment yet.

`Customer` and `SalesOrder` are record types: compile-time symbols from the
schema, not runtime values. They appear in two places, the entry point
parameter type and the record-type argument of a built-in such as
`load Customer("123")`. Using one as a value is an error that points at
`load`. A record-typed value, whether the entry point record or a loaded one,
resolves fields through the same path, so `customer.email` means the same
thing in both.

Fields are assigned on named records only; writing to an unnamed expression
such as `load Customer("1").comments` is refused because it could never be
saved.

## Syntax

```ebnf
File        := Declaration*
Declaration := UserEvent | Scheduled | Function
Function    := "fn" Identifier "(" (Parameter ("," Parameter)*)? ")" ("->" Identifier)? Block
UserEvent   := Hook EventFilter? "(" Parameter ")" Block
Hook        := "beforeSubmit" | "afterSubmit"
Scheduled   := "scheduled" Block
EventFilter := Identifier ("|" Identifier)*
Parameter   := Identifier ":" Identifier
Block       := "{" Statement* "}"
Statement   := LetStatement | SaveStatement | DeleteStatement | RemoveStatement | AddStatement | ReturnStatement
             | IfStatement | ForStatement | Expression ("=" Expression)? Terminator?
ReturnStatement:= "return" Expression? Terminator?
ForStatement:= "for" Identifier "in" Expression Block Terminator?
LetStatement:= "let" Identifier "=" Expression Terminator?
SaveStatement:= "save" Expression Terminator?
DeleteStatement:= "delete" Expression Terminator?
RemoveStatement:= "remove" Expression Terminator?
AddStatement:= "add" Expression Block Terminator?
IfStatement := "if" Expression Block ("else" Block)? Terminator?
Expression  := Unary (BinaryOperator Unary)*
BinaryOperator := "||" | "&&" | "==" | "!=" | "<" | "<=" | ">" | ">="
Unary       := "!" Unary | Postfix
Postfix     := Primary ("." Identifier | TypeArgument ("(" Arguments ")")? ("to" TypeArgument)? | "(" Arguments ")")*
TypeArgument:= Identifier
Arguments   := (Expression ("," Expression)*)?
Primary     := Identifier | String | Number | "true" | "false" | "(" Expression ")" | Query
Query       := "query" Identifier (Terminator? "where" Expression)?
```

Statements end at a newline (Go's rule: only after a token that can end a
statement) or a `;`. `//` starts a line comment. Declaration keywords, `let`,
`save`, `if`, `else`, event names, built-in names such as `log` and `load`,
and record type names are ordinary identifiers interpreted by position, never
lexical keywords. `save` and `if` begin a statement unless used as an
expression (`save.x`, `save(...)`, `save = ...`, `save == ...`), so a local
may be called `save`; `if (x) {` is an `if` with a parenthesized condition.
`true` and `false` are literals wherever an expression is expected and cannot
name a local. Binary operators are parsed by precedence climbing over a small
operator table (`src/parser/parser.ts`) that records each operator's
precedence and associativity; a new operator is a table entry.
A call may carry a type argument between the callee and its parentheses:
`load Customer("123")`. The parser records it as a name; the binder requires
it to be a record type.

## Built-ins

| Built-in        | Signature                 | Returns | Requires   |
| --------------- | ------------------------- | ------- | ---------- |
| `log.debug`     | `(details: Text)`         | Void    | `N/log`    |
| `log.audit`     | `(details: Text)`         | Void    | `N/log`    |
| `log.error`     | `(details: Text)`         | Void    | `N/log`    |
| `log.emergency` | `(details: Text)`         | Void    | `N/log`    |
| `load`          | `T(id: Text)`             | `T`     | `N/record` |
| `create`        | `T`                       | `T`     | `N/record` |
| `copy`          | `T(id: Text)`             | `T`     | `N/record` |
| `transform`     | `T(id: Text) to U`        | `U`     | `N/record` |

These are the four levels `N/log` exposes; there is no `info`.

A built-in's signature declares whether it takes a record type before the
argument list and may then return `T`, the record type supplied. That is the
whole generic mechanism: `load Customer(...)` is `Customer`,
`load SalesOrder(...)` is `SalesOrder`, with no per-built-in binder code.

**Record type lowering.** `Customer` becomes `record.Type.CUSTOMER` through
the `suiteScriptType` field on the record schema. That field is platform
metadata, not account metadata: standard records have a `record.Type`
constant, custom records do not and would be emitted as their id string.
It lives in the built-in schema layer and is never derived by transforming
names. Module locals and `context` are renamed with a `$` suffix only when a
Sail local of the same name exists, so `let record = ...` still compiles.

**Logging lowering.** `log.debug("x")` becomes
`log.debug({ title: "<entry point>", details: "x" })`. The title is the
entry point name (`beforeSubmit`, `execute`) so the execution log's Title
column says where a line came from without the author writing it. A future
two-argument form can set the title explicitly.

### Design note: inferred dependencies

Sail infers NetSuite module dependencies from semantically bound built-ins
rather than requiring explicit imports for platform features Sail
understands. The binder resolves `log.debug` to a built-in symbol that
declares it needs `N/log`; the bound `ScriptUnit` carries the set of required
modules; the emitter turns that set into `define(["N/log"], (log) => ...)`.
A user event that only writes fields still generates `define([], ...)`. The
emitter never scans source identifiers or generated text to find imports.

## Accounts and schema snapshots

The compiler is a pure function of source text and a `SchemaProvider`. It
never authenticates, never makes a network request, and never knows where a
schema came from. Everything that talks to NetSuite lives in
`src/netsuite/account`, `src/netsuite/client`, and `src/netsuite/schema`,
and is used only by the CLI:

```text
NetSuite  ->  CLI + client  ->  .sail/schema/<alias>.json  ->  SchemaProvider  ->  compiler
```

A test (`tests/netsuite.test.ts`, "compiler boundary") fails if any compiler
module imports from those directories or from `node:*`.

### Configuration and secrets

| Where | File | Contents | Committed |
| --- | --- | --- | --- |
| project | `sail.json` | `{ "account": "sandbox" }`, the default alias | yes |
| project | `.sail/schema/<alias>.json` | the pulled schema snapshot | yes |
| project | `.sail/schema/raw/` | raw NetSuite responses (`--keep-raw`) | no (git-ignored) |
| user | `~/.config/sail/config.json` | alias -> account id, OAuth client id, loopback port | no |
| secrets | macOS keychain (`sail-netsuite` items) | access and refresh tokens | no |

`$SAIL_CONFIG_DIR` overrides the user directory. On platforms without a
keychain implementation, tokens go to `~/.config/sail/credentials.json`
with mode 0600, and the CLI says so on every login; that is a development
fallback, not a secure store. No command ever writes an account id, client
id, or token into the project.

### NetSuite setup (once per account)

Sail logs in with OAuth 2.0 authorization code grant with PKCE, as a public
client, which NetSuite only allows for an Integration record you create:

1. Setup > Company > Enable Features > SuiteCloud: enable **OAuth 2.0**.
2. Setup > Integration > Manage Integrations > New. Enable **Authorization
   Code Grant** and **Public Client**, set the redirect URI to
   `http://localhost:8484/callback` (or the port you give `sail account
   add --port`), scope **REST Web Services**. Save and note the client id.
3. The role you log in with needs **REST Web Services** and **Log in using
   OAuth 2.0 Access Tokens**, plus view permission on the record types
   whose metadata you pull. A dedicated read-only role is the least
   privilege that works; Sail never writes to the account.

Then `sail account add <alias>` takes the account id (for example
`1234567_SB1`) and the client id. The access token lives one hour and is
refreshed automatically; NetSuite's refresh token for this grant lives seven
days, after which `sail auth login` runs again.

### What `schema pull` does

It reads the SuiteTalk REST **metadata catalog**: the record type list, then
one JSON Schema per type (`Accept: application/schema+json`). That is the
only documented, OAuth-reachable metadata source that needs nothing deployed
to the account. The raw documents are normalized in
`src/netsuite/schema/normalize.ts`:

| NetSuite says | Sail field type |
| --- | --- |
| `boolean` | `Bool` |
| `number`, `integer` | `Number` |
| `string` | `Text` (a fixed `enum` is kept under `values`) |
| `string` with `format: date` / `date-time` | `Date` |
| object with an `id` (a reference) | `Ref`, with `refTarget` when the `$ref` names a catalog type |
| anything else | `Unknown` |

`Date`, `Ref`, and `Unknown` are deliberately not `Text`: such a field can
be read, but no Sail operation accepts it yet, so the compiler is incomplete
about it rather than wrong. Writability is `readOnly` from the catalog, the
only signal it has; its absence does not prove SuiteScript will accept a
write. `required` is set only when the catalog marks a property required or
non-nullable. Custom fields are recognized by the `x-ns-custom-field` key
or by NetSuite's fixed `cust*` script id prefixes. Sublists and hypermedia
links are omitted and listed under the record's `netsuite.omitted`.

Two things are derived from NetSuite naming rules rather than stated by the
metadata, and are marked `DERIVED` in the normalizer: the SuiteScript record
id and field ids are the REST names lowercased (`salesOrder` -> `salesorder`,
`companyName` -> `companyname`). The REST names are kept under `netsuite`
on every record and field so a mismatch can be found and fixed in one place.
`record.Type` constants are not derived at all: `src/netsuite/platform/record-types.ts`
is a hand-maintained table, and a record missing from it is addressed by its
id string, which is the constant's value.

Snapshots are deterministic (every object's keys sorted) and a pull that
changes nothing leaves the file untouched, including its `pulledAt`. The
header carries the account id, which is not a credential. `sail schema diff
<a> <b>` compares two snapshots (aliases or files) structurally: records and
fields added or removed, types and writability changed. A type the role
cannot read is skipped with a message rather than aborting the pull; only an
authentication failure aborts. `sail schema inspect <alias>` (after a pull
with `--keep-raw`) prints the raw responses' structure, property keys,
type and format distribution, `$ref` targets, enum samples, and custom-field
markers, with no labels, so the normalizer's assumptions can be checked
against the real account.

## Editor support

`sail lsp` runs a Language Server Protocol server on stdio. Any LSP client
can use it; nothing assumes a particular editor. For Zed, a language
configuration that runs `sail lsp` for `*.sail` files is all that is needed;
for VS Code, a thin extension that spawns the same command.

The server provides diagnostics, completion, hover, go-to-definition, find
references, rename, and document symbols, and every one of them comes from
the same pipeline the compiler runs: lexer, parser, binder, analysis. `src/lsp/` has
no language rules of its own. It asks `src/semantic/query.ts`, a read-only
query surface over the analyzed document, which answers from the bound tree,
the symbol table the binder recorded (every local and the region where its
name is in scope), and the binder's own name resolution. Completion decides
*where* the cursor is from the token stream, since the syntax tree is often
incomplete exactly there, and then asks the semantic document *what* names
mean; it never resolves a name itself. Field completion after a `.` takes
the bound expression that ends at the dot, whatever it is, and lists the
fields of its record type, so `customer.`, `load Customer("1").`, and
`create SalesOrder.` take one path, and a custom field appears the moment it
is in the snapshot. The binder keeps every expression it bound in a table on
the unit, including expressions inside statements that failed to parse
completely, which is why the receiver of a half-typed member access is
still known.

Two parser changes make this work on code that is being typed: a statement
that fails to parse is skipped to the end of that statement and the rest of
its block still binds, and a block left open at the end of the file is
reported but kept. Both also give the command line more diagnostics per run.

Each change re-analyzes the whole document; the full pipeline takes
microseconds on the examples and well under a millisecond on a 200-line
script, so incremental parsing is not needed yet. The schema comes from the
same resolution the CLI uses: `sail.json` found by walking up from the file,
then `.sail/schema/<alias>.json`, reloaded when either file changes on disk.
Without a project the built-in sample is used; with a project whose snapshot
is missing, the file gets a warning at its first line and the sample is used
until `sail schema pull` has run. The server never touches the network.

### Symbols, references, and rename

`src/semantic/symbols.ts` answers "what is named here?", "where is it
declared?", and "where else is it named?" from object identity in the bound
model: a parameter or `let` is one `LocalSymbol` shared by its declaration,
the symbol table, and every reference; a field is the record's one
`FieldSchema` object, so `Customer.comments` and a `SalesOrder.comments`
are different symbols even with the same script id; a record type is its
`RecordSchema`; a built-in is its registry entry. References are found by
walking the bound nodes, including the expression table, and comparing
identity, so a reference inside a statement that failed to bind for another
reason still counts and spelling never does. Find References works for all
four kinds; rename only for locals, because fields and record types are
NetSuite names owned by the schema and built-ins are the language's.

A rename is refused, with the reason, when the new name is not an
identifier or is a reserved word (`let`, `if`, `else`, `save`, the entry
point keywords, `true`, `false`), when another local with that name is in
scope anywhere the renamed local is (scope regions are nested or disjoint,
so any overlap means one declaration would see the other, which the binder
forbids), or when a built-in with that name is used inside the renamed
local's scope, since a local shadows built-ins and the use would silently
change meaning. A name the JavaScript backend has to rename, such as
`record` or `context`, is a valid Sail name and is accepted; the emitter's
existing hygiene handles the generated code.

### Semantic tokens and signature help

The server emits semantic tokens (`textDocument/semanticTokens/full`) from
the bound model, so a theme that understands the standard LSP categories
styles Sail without knowing the language. The legend uses only standard
names:

| Sail | token type | modifiers |
| --- | --- | --- |
| record type, wherever written | `type` | |
| user function | `function` | `declaration` at the declaration |
| `load`, `create`, `copy`, `transform` | `function` | `defaultLibrary` |
| `log` and `log.debug` | `namespace`, `method` | `defaultLibrary` |
| entry point and function parameters | `parameter` | `declaration` at the declaration |
| `let` locals, loop variables | `variable` | `declaration` at the declaration |
| body field, line field, query field, sublist, `id` | `property` | `readonly` when the schema says so, `modification` on an assignment target |
| event filters (`create \| edit`) | `enumMember` | |
| `beforeSubmit`, `afterSubmit`, `scheduled`, `fn`, `let`, `if`, `else`, `for`, `in`, `query`, `where`, `save`, `delete`, `add`, `remove`, `to`, `return`, `true`, `false` | `keyword` | |
| string and number literals | `string`, `number` | |

Classification is by what bound at each position, never by spelling: in
`let where = "x"` the `where` is a variable, and in `query Customer where
email != ""` it is a keyword and `email` is the Customer field. Entry point
words are keywords rather than function declarations because they are
syntax, not names the author chose. `true` and `false` are keywords because
LSP has no boolean token type. Comments and operators carry no semantic
token; a Tree-sitter grammar will highlight those. The intended stack is
basic syntax from a grammar plus these semantic tokens on top, but the
tokens are useful on their own and the grammar is not written yet.

Zed consumes this server over stdio, but to my knowledge Zed highlights
through Tree-sitter and does not yet apply LSP semantic tokens, so in Zed
the highlighting will come from the grammar once it exists; VS Code and
Neovim apply the tokens today. Nothing in the server is editor-specific.

Signature help (`textDocument/signatureHelp`, triggered by `(` and `,`)
finds the innermost open call on the token stream, so it works while the
call is incomplete, counts the active argument, and resolves the callee by
name the way the binder would. User functions show their signature, built-ins
show theirs, and a record operation is specialized to the written type:
`load Customer(id: Text) -> Customer`. Too many arguments still show the
signature; the diagnostic reports the count.

The editor consumes only the normalized snapshot contract. A future change to
`src/netsuite/schema/normalize.ts` after live validation changes what the
snapshot says, not how the editor reads it.

## Pipeline

```text
.sail source
  -> src/lexer      tokens with spans
  -> src/parser     AST: syntax only, names unresolved
  -> src/semantic   binder: resolves names against a SchemaProvider and the
                    built-in registry, reports SAIL1xxx diagnostics, produces
                    a ScriptUnit (bound model) with inferred dependencies
  -> src/semantic   analysis: path-sensitive checks over the bound model
                    (SAIL2xxx warnings)
  -> src/netsuite   emitter: ScriptUnit -> SuiteScript 2.1 text
  -> src/lsp        language server over the same analyzed document (src/semantic/query.ts)
```

`src/compiler.ts` is the pure facade. `src/cli` is the only module that touches
the file system. The compiler never performs network IO; schemas arrive through
the `SchemaProvider` interface in `src/schema/provider.ts`, and
`schemas/builtin.json` is a hand-written snapshot in the same shape
`sail schema pull` writes. Built-ins are declared in
`src/semantic/builtins.ts` and lowered in `src/netsuite/emit.ts`. Sail's
value types (`Text`, `Number`, `Bool`, `Void`, record types, and
`Sequence<T>`) are in `src/semantic/types.ts`.
